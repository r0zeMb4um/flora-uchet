# Полный аудит пилотной версии (09.11.2026)

Проверено: формулы и ядро, схема данных, согласованность отчётов, граничные и «нелепые» данные, безопасность, надёжность, нагрузка (по квотам Google), документы против кода.

## Как проверяли
- 145 автотестов, включая случайную симуляцию (`shift.fuzz`: >5 000 операций, остатки/касса/долги сверяются с журналом после каждой).
- Сверка колонок: `docs/DATA_MODEL.md` против `infra/schema.js` — совпадают.
- Перекрёстная сверка на трёх сменах: выручка периода = сумма смен = сумма чеков в Excel = сумма по дням; ЗП периода = сумма ЗП смен; прибыль = формула; продано по «топу» = движения склада. Всё сошлось.
- Пробы «нелепых» входных данных, пробы защиты от обмана флориста (см. D28), проверка выгрузки на «формулы в ячейках».
- Квоты Apps Script — по официальной странице Google (developers.google.com/apps-script/guides/services/quotas).

## Проверено и в порядке
- **Формулы:** округление «0,5 вверх» целочисленно; процент флориста делится на число флористов одной формулой; ЗП по условиям на момент открытия смены; «выдано + к доплате = начислено»; расчёт кассы; прибыль.
- **Деньги и остатки:** нельзя продать больше остатка, оплата не расходится с итогом, возвраты не больше оплаты, долг не уходит в минус, остатки = журнал.
- **Надёжность записи:** повтор с тем же `op_id` не дублирует; обрыв на любом шаге дописывается; зависшие операции ночью переходят в «не прошла».
- **Безопасность:** подпись Telegram проверяется на каждый запрос, роль и точка берутся из таблицы сотрудников по проверенному ID; токен только в свойствах скрипта; вывод в чат и в кассу экранируется.

## Открытые вопросы и предложения по пилоту

### Нужны решения владельца или Кирилла
| № | Тема | Суть | Предложение |
| --- | --- | --- | --- |
| P1 | Прибыль «по закупкам» | Сейчас прибыль = выручка − закупки − ЗП − расходы. Если товар купили раньше, а продали позже, прибыль скачет (в демо она минусовая) | Добавить вторую цифру «по себестоимости проданного» (количество × последняя закупочная цена) рядом с нынешней, объяснить разницу одной строкой |
| P2 | Закупка за 0 или за копейки | Приход «10 шт за 0 ₸» ставит закупочную цену 0, и брак/недостачи старого товара считаются в 0 ₸ | Не менять закупочную цену, если сумма накладной 0 (подарок от поставщика), либо хранить среднюю по партиям. Решает владелица |
| P3 | `cash_tolerance` | Поле допуска расхождения кассы есть в настройках, но нигде не используется | Решить: допуск (например до 500 ₸ — не считать расхождением в «Контроле») или убрать поле |
| P4 | Одинаковые имена покупателей | Три «Иванова» с разными долгами смешиваются в списке | Пометка (улица/магазин) при создании; слияние дублей владелицей |
| P5 | Очередь без связи | Без интернета можно провести только продажу и букет; приход, расход, возврат — нет | Для киоска в торговом центре расширить очередь на расход и приход (после пилота, по жалобам) |

### Для самого пилота
- **Что мерить за неделю параллельно с тетрадью:** расхождение кассы по сменам; время продажи (цель — до 20 секунд); число отказов сервера и «непроведённых» очередью; сколько раз флорист обращался к владелице за правкой.
- **Критерии успеха недели:** все смены сошлись с тетрадью по выручке до тенге; ни одного дубля чека; владелица смотрит отчёт без звонка флористу; ноль потерянных продаж в очереди.
- **Сезонные пики** (14 февраля, 8 марта): много предзаказов за день — экран «Заказы» и календарь выдач готовы, но заранее подготовьте минимумы по остаткам и отдельную закупку.
- **Обучение:** 15 минут показа каждому флористу по `docs/PILOT_CHECKLIST.md`; первую неделю владелица смотрит блок «Контроль» каждый вечер.
