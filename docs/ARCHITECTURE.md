# Архитектура (этап 1)

Как устроен продукт внутри: из каких частей, как идёт запрос, где какие подводные камни и как они закрыты. Дополняет `docs/TZ.md` и `docs/DECISIONS.md`.

## 1. Общая схема

```
Флорист / владелица
   │
   ├── Telegram-чат ──(вебхук: update_id)────────┐
   │                                             ▼
   └── Mini App (GitHub Pages) ──(text/plain:   Apps Script — ОДНО веб-приложение, ОДИН doPost
        initData + op_id + действие)──────────►  ├── роутер: Telegram или Mini App
                                                 ├── проверка: кто пишет → staff → клиент, точка, роль
                                                 ├── блокировка → логика операции → запись
                                                 └── уведомления в Telegram (после блокировки)
                                                         │
                                                         ▼
                                                 Google Таблица (листы из DATA_MODEL.md)
Триггеры по времени: 22:00 напоминание · ночной бэкап · сверка остатков · проверка вебхука
```

## 2. Три слоя кода

| Слой | Папка | Что делает | Google API |
| --- | --- | --- | --- |
| Ядро | `apps-script/core/` | `calc.js` — формулы; `ops.js` — проверяет операцию и возвращает **план записи**: какие строки в какие листы, как меняются остатки и статусы. Хранилища не знает | нет |
| Адаптеры | `apps-script/infra/`, `bot/`, `api/` | Читают и пишут листы, говорят с Telegram, проверяют подписи | да |
| Интерфейс | `miniapp/` | Экраны Mini App | нет (только запросы к doPost) |

Правило зависимостей: ядро не вызывает адаптеры. Поэтому вся логика смены проверяется в Node на «таблице в памяти» (`tests/shift.sim.test.js`), без Google.

**Один файл формул на три места.** Apps Script не понимает `import/export`, поэтому файлы ядра пишутся в «общем» стиле: функции в глобальной области + в конце `if (typeof module !== 'undefined') module.exports = {...}`. Так один и тот же `calc.js` работает в Apps Script, в Node (тесты) и в браузере (Mini App показывает «Итого» по той же формуле). Скрипт выкладки копирует `calc.js` в `miniapp/js/`.

## 4. Как проводится операция

1. **Кто пишет.** Mini App: проверка `initData`. Telegram: проверка ключа в адресе вебхука. Затем `staff` по Telegram ID → клиент, точка, роль, активен ли. Клиент и точка из тела запроса не берутся никогда.
2. **Блокировка.** `LockService.getScriptLock().waitLock(10000)`. Не дождались — ответ «Касса занята, нажмите ещё раз» (op_id тот же, дубля не будет).
3. **Повтор?** Ищем `op_id` в `ops_log` (через `TextFinder`): `posted` → вернуть сохранённый `result_json` с пометкой «уже проведено»; `pending` → перейти к шагу 5 и дописать недостающее (остатки затронутых позиций при этом пересчитываются по журналу, а не прибавляются ещё раз); `failed` → отказ «операция не прошла, оформите заново» (Mini App создаёт новый `op_id`).
4. **Логика.** Читаем нужное состояние (смена, остатки из `stock_balance`, долг) и вызываем `core/ops.js`. Он проверяет правила (остаток, сумма оплат = итого, скидка, итого > 0) и возвращает план записи или отказ с понятным текстом.
5. **Запись.** `ops_log` = `pending` → строки фактов пачкой на каждый лист (`setValues`, не по одной) → состояния и `stock_balance` → `ops_log` = `posted` последним. ID строк выводятся из `op_id` (`<op_id>-1`, `-2`…), поэтому при дописывании скрипт видит, какие строки уже есть, и не задваивает их.
6. **Снять блокировку**, затем отправить уведомления в Telegram. Сетевые запросы к Telegram внутри блокировки не делаем, чтобы блокировка была короткой.

## 5. Подводные камни и как они закрыты

| Камень | Что будет, если не закрыть | Решение |
| --- | --- | --- |
| Apps Script не видит заголовки запроса | Нельзя проверить секретный заголовок Telegram; любой, кто узнал адрес, шлёт «обновления» от имени бота | Секретный ключ в адресе вебхука: `…/exec?k=<WEBHOOK_KEY>`. Ключ — длинная случайная строка в Script Properties. Без верного ключа — тихий отказ |
| Ответ вебхука через `ContentService` | Ошибка 302, Telegram копит очередь и повторяет | Ответы Telegram — только `HtmlService.createHtmlOutput()`. Ответы Mini App — JSON через `ContentService` (браузер переадресацию проходит сам) |
| Ошибка в коде при обработке обновления Telegram | Telegram повторяет одно и то же обновление бесконечно, бот «зависает» | Весь вебхук в `try/catch`, ответ всегда 200. Ошибка → в `audit` и сообщение администратору. Повторы отсекаются по `LAST_UPDATE_ID` |
| Telegram шлёт обновления параллельно (до 40 соединений) и не по порядку | Защита по `LAST_UPDATE_ID` выбросит «опоздавшее» настоящее обновление | `setWebhook` с `max_connections=1`: обновления идут строго по одному и по порядку. Проверка и запись `LAST_UPDATE_ID` — под блокировкой |
| Таблица сама меняет формат данных | `2026-11-06` превращается в дату, `001` в число 1, длинный Telegram ID — в «1,23E+09» | `setup()` ставит колонкам ID, дат и Telegram ID текстовый формат `@` |
| Предел размера Таблицы (10 млн ячеек) | Через несколько лет или при нескольких магазинах запись остановится | Ежедневная проверка заполненности; при 50% — сообщение администратору; архив прошлых лет в отдельную Таблицу или переход на этап 2 |
| Операция зависла в `pending` (флорист не повторил) | Её строки лежат в листах, остатки искажены | Решение D14: ночью `pending` старше часа → `failed`, остатки пересчитываются по журналу |
| Код в открытом репозитории (бесплатный GitHub Pages) | Секрет, попавший в git, виден всем навсегда | Решение D15: секреты только в Script Properties; `.gitignore` для `.clasprc.json` и `.clasp.json` с ID скрипта; проверка в CI, что в коде нет похожих на токен строк |
| Новое развёртывание меняет адрес | Ломаются вебхук и Mini App одновременно | Всегда обновляем одно и то же развёртывание: `clasp deploy -i <DEPLOYMENT_ID>`. Делает только `scripts/deploy.mjs`, руками не развёртываем |
| Запросы из Mini App с `application/json` | Браузер блокирует запрос (CORS) | `fetch` с `Content-Type: text/plain`, тело — JSON-строка |
| Подделка запросов Mini App | Чужой человек проводит продажи | `initData`: ключ = HMAC-SHA-256(«WebAppData», токен бота), подпись = HMAC-SHA-256(ключ, строка проверки). В Apps Script — `Utilities.computeHmacSha256Signature` с массивами байт. `auth_date` не старше 12 часов |
| Таблица медленная, листы растут | Экран продажи открывается 3–5 секунд, через месяц хуже | Остатки — из `stock_balance`; каталог и остатки — в `CacheService`; запись пачками; Mini App загружает каталог и остатки один раз при открытии |
| Скорость ответа Apps Script 1–3 с | Флорист жмёт «Провести» второй раз | Кнопка блокируется до ответа и показывает «Проводим…»; повтор с тем же `op_id` безопасен |
| Обрыв на середине записи | Половина продажи в таблице | Шаг 5 раздела 4: `posted` последним, отчёты учитывают только `posted`, повтор дописывает |
| Ручная правка таблицы | Цифры перестают сходиться | Таблица защищена: редактор — только аккаунт проекта; владелица — просмотр; доступ по ссылке выключен |
| Таймзона | Смена «после полуночи» уезжает в другой день | `appsscript.json` → `Asia/Almaty`; все даты формирует сервер, не телефон |
| Лимиты Google (6 мин на запуск, 30 одновременных, 20 000 запросов к Telegram в сутки) | На одном ларьке не грозит; при нескольких магазинах в праздники — да | Следим в ежедневной проверке; при росте — этап 2 |

## 6. Mini App

- Обычные HTML + CSS + JavaScript (модули браузера), без сборщика: меньше движущихся частей, публикуется как есть.
- Telegram Web App SDK: `MainButton` («Провести 15 000 ₸»), `BackButton`, `HapticFeedback`, тема.
- Черновик формы и её `op_id` хранятся на телефоне (`localStorage`) до ответа «проведено». Без интернета — честное сообщение, повтор с тем же `op_id`.
- Визуал — отдельная задача (`docs/BACKLOG.md`). До неё — текущие токены из `docs/DESIGN.md`.

## 7. Выкладка и автоматизация

| Что | Как |
| --- | --- |
| Проверка при каждом сохранении в GitHub | `ci.yml`: `npm test` (эталонная смена + симуляция). Красный — выкладка запрещена |
| Mini App | `pages.yml`: после зелёных тестов публикуется на GitHub Pages |
| Apps Script | `npm run deploy` на компьютере: тесты → `clasp push` → `clasp deploy -i <DEPLOYMENT_ID>` → `getWebhookInfo` (нет ошибки, очередь 0) |
| Напоминание о незакрытой смене | Триггер каждые 15 минут: если время ≥ `reminder_time` точки и смена открыта — сообщение флористу и владелице (один раз за день) |
| Бэкап | Ночной триггер: копия таблицы в папку Google Диска, старше 30 дней — удаляются |
| Сверка остатков и зависшие операции | Ночной триггер: `pending` старше часа → `failed` (D14); `stock_balance` против суммы `stock_moves`; пересборка листа `summary` |
| Заполненность Таблицы | Ежедневно: число ячеек; при 50% от предела — сообщение администратору |
| Здоровье бота | Ежедневно `getWebhookInfo`; ошибка или очередь > 0 — сообщение администратору |
| Новый магазин | Функция-шаблон в `setup.js`: копия таблицы, настройки, сотрудники, ссылка-приглашение |

## 8. Путь к этапу 2

Сервер на Node.js (решение D1). Переезжают как есть: `core/` целиком, эталонный тест, Mini App. Переписываются только адаптеры: вместо листов — база данных (настоящие транзакции вместо `pending → posted`), вместо `LockService` — блокировки базы, вместо триггеров — планировщик сервера.
